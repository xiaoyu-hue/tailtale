## 1. 架构目标与约束

架构不是越先进越好，而是**由约束倒逼出来的**。书时的硬约束：

| 约束 | 对架构的要求 |
|---|---|
| 本地优先，无服务端 | 全部状态与业务逻辑跑在浏览器；持久化只依赖 IndexedDB / localStorage |
| 零成本运营，无后端 | 不能出现"等接口"的数据流；模块间通信必须在端内完成 |
| PWA 离线可用 | 产物是一个整体包；不做运行时按模块懒加载 |
| 单人开发 + AI 协作 | 结构必须自解释：看目录就知道功能放哪，降低上下文切换成本 |
| M1→M7 持续加功能 | 新功能必须是"新增模块"，而不是"修改老文件" |
| 数据不出浏览器 | 模块边界即数据边界；跨模块共享必须显式经公开 API |

**架构目标一句话**：让每个新功能成为一个自包含的模块，新功能只往仓库里"加文件夹"，不改动已有模块的内部。

## 2. 现状评估（M1 交付后）

M1 代码共 15 个文件、约 1256 行，已实测通过 28 项冒烟测试。评估基于实际代码，不是印象。

### 2.1 保留（经实战验证的正确决策）

| 决策 | 位置 | 为什么保留 |
|---|---|---|
| 无路由库，union 类型 + state 管理导航 | App.tsx | 5 个页面，引 react-router 属过度设计；现有方案零依赖且全权控制转场 |
| IndexedDB + Promise 封装 | lib/db.ts | 本地优先的正确选型；封装薄而够用 |
| 文件内容哈希作为书籍 ID | lib/hash.ts | 同一文件跨设备续读的基石，设计优雅 |
| 阅读进度 400ms 防抖持久化 | pages/Reader.tsx | 正确的性能模式，避免高频写库 |

### 2.2 将随功能堆叠而破裂的 6 个点（按严重度排序）

| # | 问题 | 证据（现状） | 破裂时点 |
|---|---|---|---|
| 1 | **App.tsx 是上帝组件**：书架状态、路由、全部跨页 handler 集于一身 | App.tsx 114 行，含 books state + 5 个 handler | M2 加全局阅读计时、M3 加金币后，每个新功能都要回来改 App.tsx，回归风险累积 |
| 2 | **lib/ 是扁平杂物层**：平台能力（db、hash）与领域逻辑（chapters、books）混放 | lib/ 4 个文件横跨两个抽象层 | M2-M7 会继续扔进 timer/coins/pet/ai/backup，最终 10+ 文件平铺难辨职责 |
| 3 | **跨模块共享状态无机制**：金币余额要同时显示在首页、商店、宠物页 | 目前只有 books 一个共享 state，靠 App.tsx props 层层传 | M3 起 props 钻透 3 层页面，App.tsx 膨胀爆炸 |
| 4 | **横切关注点无家可归**：阅读计时在用户切走 Tab 后必须继续跑 | 计时只能挂在 Reader 页面组件里，组件卸载即停 | M2 第一天就会撞上：切到宠物页计时就停了，产品核心逻辑直接错误 |
| 5 | **types.ts 全局单文件**：所有类型堆一处 | types.ts 24 行尚可 | 七个模块的类型都往里加，改 A 模块类型与 B 模块产生合并冲突 |
| 6 | **IndexedDB 无迁移预案**：M2 加金币 store、M3 加宠物 store 都要升版本号 | db.ts 无 upgrade 回调管理 | 老用户升级后数据 store 缺失，静默丢数据 |

**结论**：M1 架构对 M1 是合格的；对 M2-M7 不及格。现在重构成本最低（功能还没堆上来），再拖两个里程碑，改造就是伤筋动骨。

## 3. 目标架构总览

### 3.1 四层结构

```
src/
├── app/            应用外壳：导航、全局 Provider、应用级装配
├── modules/        领域模块：每个功能域一个自包含文件夹
├── platform/       平台能力：与业务无关的基础设施
└── shared/         跨模块共享：UI 原子组件、通用 hooks、通用工具
```

**依赖方向（硬规则）**：

```
app  ──► modules ──► platform
 │          │
 └──► shared ◄──────┘
```

- app 可依赖 modules 与 shared；modules 可依赖 platform 与 shared
- **modules 之间禁止直接 import 对方内部文件**，只准 import 对方 `index.ts` 公开 API
- platform 不准依赖任何上层；shared 不准依赖 modules
- 跨模块通信只走两条通道：对方公开 API，或 platform/events 事件总线

### 3.2 模块地图（与里程碑对齐）

| 模块 | 职责 | 里程碑 | 状态 |
|---|---|---|---|
| books | 书架：导入/删除/三态/书籍元信息 | M1 已有 | 待迁入 |
| reader | 阅读器：章节拆分/进度/字号 | M1 已有 | 待迁入 |
| gamification | 游戏化中枢：阅读计时/打卡/经验/金币 | M2 | 新建 |
| settings | 全局偏好：主题/字号/界面皮肤/数据备份 | M2 起建 | 新建 |
| pet | 宠物：属性/成长/喂食/玩耍 | M3 | 新建（S1-S4 已上线：数据层/商店闭环/UI/羁绊时刻） |
| shop | 商店：金币消费/物品 | M3 | **缓建**（偏差说明见下） |
| toolbox | 工具集：番茄钟/白噪音/统计/书摘导出/TTS/全文搜索 | M4 | 已上线（v1.13.0） |

## 4. 模块划分详解

模块的准入标准：**有独立数据、独立状态、独立 UI 的功能域**。工具番茄钟这类纯 UI 小功能并入 toolbox，不单独建模块（避免过度设计）。

| 模块 | 拥有数据（IndexedDB store） | 公开 API 草案（index.ts） | 被谁依赖 |
|---|---|---|---|
| books | books, contents | `useBooks()` `importTxt()` `removeBook()` `<BookList>` | app, reader |
| reader | （读 books 的 contents，不自有 store） | `useReadingProgress()` `openReader()` `<ReaderPage>` | app, gamification（读时长） |
| gamification | sessions, coins, checkins | `useCoins()` `useTodayStats()` `startReading()` `pauseReading()` | app, pet, shop, toolbox |
| settings | settings | `useSettings()` `updateSettings()` | app, reader（字号） |
| pet | pet | `usePet()` `usePetLoaded()` `usePetMood()` `refreshPet()` `useSnack(id)` `strokeCat()` `toggleSleep()` `acknowledgeBonds()` `<CatStage>` `<StatBars>` `<SnackButtons>`（S1-S3 已实现） | app, shop |
| shop | （M3 无自有数据；购买编排在 app 层） | （无模块 API；UI 为 app/views/ShopView + pet/ui/SnackButtons） | app |
| toolbox | （按工具定，番茄钟无持久化） | `<ToolboxPage>` 及工具入口 | app |
| ai | aiConfig | `useAiConfig()` `explainText()` | reader（长按解读书摘） |
| games | game_records / game_matches | `useGameRecord(id)` `useHostMode()` `setHostMode()` `settleGameRound()` `recordDraw()` `refreshMatches()` `useMatchHistory()` `fetchHostLine()` `refreshGames()` `<GamesView>` | app；经公开 API 依赖 gamification（`awardCoins`）与 ai（`chatOnce`）；vendored `vendor/gomoku/`（五子棋 AI，模块内消费） |

**设计说明**：gamification 是唯一被多方依赖的"中枢模块"，因此它的公开 API 必须最先稳定；books 与 reader 保持 M1 的边界（reader 不写 books 的元信息，只通过 books 公开 API 汇报进度）。

> **偏差说明（M3/S2 记录）：shop 模块缓建。** 原规划 shop 自有 inventory store、暴露 `buy()`。M3 实际落地时发现：M3 范围的"商店"只是四件零食的即买即用列表——商品数据在 pet 的 `SNACKS` 表、金币在 gamification 的钱包、购买编排（扣币→使用→回滚）在 app 层 `commerce.ts`，shop 没有任何独立数据、独立状态、独立 UI，不满足第 4 节模块准入标准。按"避免过度设计"原则不为空壳建模块：商店页由 `app/views/ShopView.tsx`（app 层视图）+ `pet/ui/SnackButtons.tsx`（pet 模块 UI）组合而成。若后续出现库存、限购、装扮背包等真实状态，再按标准晋升为模块。

```
modules/reader/
├── index.ts     唯一对外出口：公开 API + 公开组件，内部实现不暴露
├── model.ts     数据类型 + 纯函数（章节拆分、进度计算、状态机）——无副作用，可单测
├── store.ts     模块状态：useSyncExternalStore 订阅源
├── service.ts   副作用：IndexedDB 读写、文件读取、计时器
└── ui/          模块专属组件：ReaderPage.tsx / ChapterList.tsx / FontSizeControl.tsx
```

**各文件职责边界**：

| 文件 | 允许做的事 | 禁止做的事 |
|---|---|---|
| model.ts | 纯计算、类型定义 | import store/service/ui 任何东西 |
| store.ts | 持有状态、发通知 | 直接碰 IndexedDB（经 service） |
| service.ts | 持久化、IO、计时器 | import ui |
| ui/ | 渲染、调 store、调 service | 被别的模块直接 import |
| index.ts | 选择性 re-export | 实现逻辑（只做出口） |

配套一条执行手段：在仓库根放 `eslint-plugin-boundaries` 或最轻量的 `.eslintrc` import 规则（M2 迁移时启用），把上述规则交给工具强制，不靠人记。

## 6. 横切关注点方案

### 6.1 阅读计时（M2 最关键需求）

计时**不是页面功能，是应用级服务**：计时器住在 `modules/gamification/service.ts`，与 React 组件生命周期解耦，刷新页面后能恢复会话。

**计时口径（v1.3 修正，以 PRD 为准）**：PRD §3.1.1 的权威表述是"页面可见且书籍打开时累计"。阅读页是全屏沉浸形态（无底部 Tab 栏），用户离开阅读页的唯一操作是返回书架——语义上就是"合上书"。因此实际口径：

```
用户打开书 ──► reader 调 gamification.startReading(bookId)
                  │  service 内 setInterval(1s) 累计
                  │  + document.visibilitychange：切浏览器后台暂停累计（防挂机）
用户返回书架 ────► reader 卸载即 stopReading()：停表并持久化会话（合上书）
用户刷新/误关 ───► pagehide 尽力持久化；重开同一本书从断点继续计时
金币结算 ──► 按累计时长推导增量：XP 每整分钟 1:1，金币每 30 分钟 +10，
              经事件总线广播（wallet:changed）
```

> **偏差说明（v1.3 记录）**：v1.0/v1.2 原稿写的是"用户切 Tab/退出，reader 卸载不停止计时；只有合上书/超过 5 分钟无操作才停"。该口径与 PRD 矛盾，且在本项目的全屏阅读形态下"切 Tab 停不停"没有对应 UI 场景（应用内没有 Tab 可切，离开即回书架）。S3 按 PRD 实现并经用户确认。若未来阅读页改为非全屏形态（M2 之后可能出现"边读边逛"需求），本条需重新评审。

Reader 页面只负责"打开时 startReading、关闭时 stopReading"，不知道金币存在。

### 6.2 事件总线（跨模块广播）

放 `platform/events.ts`，最小实现（约 25 行，typed emitter）：

```ts
// 用法：gamification 结算后 emit('coins:changed', balance)
//      pet 模块监听后自动刷新饱食度动画——pet 永远不需要 import gamification
```

必须走事件总线的场景（已实现）：wallet:changed（金币/XP/今日分钟变化）、checkin:done（打卡成功）、book:finished（读完一本书，books 广播、gamification 发奖）、reading:bond_moment（阅读会话每跨满 30 分钟，gamification 广播、pet 加好感并记未看羁绊）。不需要的场景：读一次数据（直接调对方公开 API 即可，别滥用事件）。

**反例确认（M3/S1）**：pet 模块的互动动作（喂食/抚摸/睡觉）会改变宠物状态，首页速览、宠物页、商店页都要看到最新值——但这不构成事件总线的用例：各方直接 `usePet()` 订阅 pet store 即可（React 外部 store 的精确订阅就是干这个的）。动作经 store 层封装，DB 读写成功后直接用返回值同步内存状态，无需绕道总线。判定标准：**有跨模块副作用（发奖、联动）才用事件；纯状态展示用订阅。**

**羁绊时刻是 pet 唯一走总线的场景（M3/S4）**：连续阅读 30 分钟的好感奖励由 gamification 的会话累计值触发（每跨满一个 30 分钟块广播一次），事件到达 pet 后改变 pet 状态（好感 +5、未看计数 +1）——这是「gamification 的副作用落在 pet 上」的跨模块联动，符合上述判定标准，故新增 `reading:bond_moment`；反之 pet 自身状态变化没有任何跨模块消费者，仍不走总线。会话侧以 `bondsAwarded` 计数防刷新重触发（与金币/XP 的已发放值同机制），计数落库无需 DB 迁移（旧行按 0）。

### 6.3 跨模块共享状态

不引 Zustand/Redux。`platform/store.ts` 提供一个约 20 行的 `createStore` 工厂（基于 `useSyncExternalStore`，React 18 内置），每个模块的 store.ts 用它创建。全局只有三类状态：路由（app）、模块自有状态（各自 store）、持久化配置（settings）。

### 6.4 IndexedDB 迁移机制

`platform/db.ts` 集中管理 upgrade：每加一个 store 登记一条迁移函数，版本号只增不改：

```ts
const MIGRATIONS = [
  { version: 1, upgrade: createBooksStores },      // M1 已有
  { version: 2, upgrade: createGamificationStores }, // M2
  { version: 3, upgrade: createPetStores },          // M3
];
```

老用户打开新版本时按序执行，杜绝静默丢数据。

## 7. 状态管理选型（决策记录）

| 方案 | 判断 | 理由 |
|---|---|---|
| 继续 props 层层传（现状） | ✗ 不可行 | M3 起金币要钻透 3 层页面，App.tsx 爆炸 |
| Redux Toolkit | ✗ 过度设计 | 为一个数字（金币）引入 boilerplate 工厂，单人项目维护成本大于收益 |
| Zustand / Jotai | △ 可行但不选 | 确实轻量，但项目状态总量极小（一本书、一只猫、几个计数器），20 行自建 store 覆盖全部需求，少一个依赖少一条供应链义务 |
| Context + useReducer | ✗ 不选 | 高频更新（每分钟计时）会引发消费 context 的整棵树重渲染 |
| **useSyncExternalStore + 自建 createStore** | ✓ **选定** | React 18 官方外挂store 模式；精确订阅避免无效重渲染；零依赖；单文件可读 |

## 8. 不过度设计的明确边界

写进文档防止未来自己手滑：

| 不做 | 原因 |
|---|---|
| 不引路由库 | 5 个页面，union 类型路由已work |
| 不引状态管理库 | 见第 7 节 |
| 不做微前端/模块联邦 | 单应用单仓库单开发者 |
| 不做按模块代码分割/懒加载 | PWA 要求离线全量可用，分包反而劣化首屏与缓存 |
| 不写 Repository/CQRS 抽象层 | IndexedDB 封装已足够，抽象层只会增加跳转成本 |
| 不做严格 DDD 聚合根 | 没有复杂业务不变式，"聚合"是装饰品 |
| 不给少于 80 行的功能建模块 | 并入所属模块，如番茄钟并入 toolbox |

仓库根另有：`public/library-books/`（内置公版书文本，随应用同源分发）+ `public/library-manifest.json`（书单与指纹清单）+ `scripts/clean_books.py`（构建期离线清洗管线，源文本自备，需 opencc）。书籍文本不进 SW precache（workbox.globPatterns 排除），领取后即落 IndexedDB。

**测试体系目录（1.12.0）**：`tests/*.test.mjs`（node:test 单测，与被测模块一一对应）+ `tsconfig.test.json`（测试编译清单，新增被测模块在 include 加一行）+ `scripts/smoke/smoke.py`（Playwright 端到端冒烟，一条命令自包含）+ `.github/workflows/ci.yml`（quality + smoke 双作业）。测试分层与选型详见《书时-技术栈.md》§3.7。

**reader 与模板的偏差说明**：reader 实际只有 index/model/ui 三层，无 store.ts 与 service.ts——阅读状态（进度、在读/读完）归 books store 持有（书籍是主语），阅读计时归 gamification service，reader 只做渲染与汇报，不持有任何跨页面状态。这是 S2 定下的边界，1.1.0 引入 EPUB/PDF 后维持不变：EpubReader/PdfReader 同样只调 books 公开 API。渲染引擎（epubjs、pdfjs-dist）以动态 import 按需加载：约束中的「产物是一个整体包、不做运行时按模块懒加载」针对业务模块分包（避免首屏后才出现路由级代码），引擎属于第三方大依赖，且 vite-plugin-pwa 的 autoUpdate 策略会预缓存全部构建产物（含动态 chunk），离线可用性不受影响；按格式加载反而缩小首屏体积。CbzReader / MobiReader 维持同一边界：前者经 JSZip 自行解包图片（books 只负责二进制存储与格式识别），后者经 books 公开 API openMobiBook 解析（MOBI 集成归属 books 模块，mobi.ts 为唯一入口，reader 不直接 import vendor 文件）。

**阅读器手势说明**：滑动翻页为自研 hook（`shared/hooks/useSwipe.ts`），三个阅读器共用一套方向映射（左滑/上滑 = 下一页，右滑/下滑 = 上一页），零新依赖。**iOS 适配（1.2.2）**：手势一律走原生 `addEventListener` 且 `passive: false`——iOS Safari 的规矩是手指一动系统即开始判定滚动，一旦进入滚动模式 `touchend` 不再派发、改派 `touchcancel`，不阻止滚动就等不到松手；而 React 合成事件的 touchmove 固定 passive，`preventDefault` 会被浏览器无视，这是 iOS 真机滑动失效的根因（桌面 Chromium 无此行为，合成事件测试覆盖不到，须真机验证）。移动距离超过 10px 定型后按轴阻止：TXT（axis=horizontal）只拦横向、竖滑放行原生滚动；EPUB / PDF（axis=both）横竖一律拦。`touchcancel` 只作状态重置、不触发翻页（被放行的是滚动方向，本就无翻页语义）。挂点：TXT / PDF 绑舞台 div（useEffect + ref）；EPUB 内容渲染在 epub.js 托管的 iframe 内（srcdoc 同源），绑 iframe `contentDocument`，捕获阶段 + `stopImmediatePropagation` 先于内置 snap_Snap 执行避免双翻页；CSS `touch-action`（TXT pan-y / PDF 与 iframe none）作 iOS 13+ 渐进增强，旧版本靠 JS 兜底。另修复 1.1.0 遗留死代码：原「rendered」回调把 click 监听绑到 IframeView 实例上（该类无 `addEventListener`，可选链静默跳过），点击正文切换控件栏从未生效。
