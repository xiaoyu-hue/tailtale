## 1. 版本号结构：X.Y.Z

主干是业界语义化版本（SemVer），本项目按**变更的重要程度**映射到三段：

| 段位 | 何时动 | 本项目判定标准（满足其一即升） | 示例 |
|---|---|---|---|
| **主版本号 X**.0.0 | 架构级变更 | 四层架构调整或模块重组；数据模型不兼容迁移且无自动迁移路径；核心技术栈更换（框架/构建/PWA 方案）；产品定位发生实质变化 | 0.x → **1.0.0**（M1+M2 完成，首个结构完整、可正式发布的版本） |
| **次版本号** 1.**X**.0 | 新功能上线 | 新模块、新页面、新能力上线，且向后兼容（不破坏既有数据与行为） | **1.1.0**（多格式阅读上线：EPUB / PDF 导入与渲染） |
| **修订号** 1.1.**X** | 优化修复与文档 | Bug 修复、性能优化、文案调整、配置微调、文档同步、构建脚本修补——不改变能力边界 | **1.1.1**（修一个计时边界 Bug） |

**一句话记忆：动结构升大头，加功能升中间，修修补补升尾巴。**

## 2. 版本号与里程碑（M1-M7）的关系

- 里程碑是**开发节奏**，版本号是**发布节奏**，两者解耦、互不强制对应。
- 常见形态：一个版本收尾一个或多个里程碑（如 1.0.0 = M1+M2）；一个大里程碑也可拆成多个次版本发布（如某里程碑若体量大，可 1.2.0 上半场、1.3.0 下半场）。
- README 进度段同时展示「当前版本」和「里程碑勾选」，两者不必一致，以各自口径为准。

## 3. 每次发版要改哪些位置（防遗漏清单）

按顺序逐项确认，一项不落：

1. `package.json` → `"version": "X.Y.Z"`——**版本号的唯一来源**（v1.4 起）
2. `src/app/views/ProfileView.tsx` → 「我的」页最底部（「隐私说明」卡片下方）的脚注，固定格式 `书时 TailTale vX.Y.Z · <阶段主题>`——这是应用内唯一对外可见的版本号。其中 `vX.Y.Z` 由构建注入自动同步（vite.config.ts 读 package.json，无需手改）；**每次发版只需确认脚注中的「阶段主题」文案已更新为新版本主题**，用户点名每次必改，漏改会被用户当场发现
3. `README.md` → 「当前进度」段标题版本号、正文表述、部署说明
4. `CHANGELOG.md` → 把「未发布」段内容搬进正式段，写版本号 + 发布日期，「未发布」段清空为占位
5. `docs/书时-架构设计.md` → 仅当架构有实质变化时升文档版本头并追加修订记录；纯功能/修复发版不动
6. 其它 docs（PRD / 技术栈 / 合规）→ 仅当对应文档内容有实质变化时升版本头

> 注意区分：`src/platform/db.ts` 里的 `version: N` 是 **IndexedDB 数据库 schema 版本**，与应用版本号完全独立，按迁移需要递增，不随发版改动。

## 4. 发版流程（从改完代码到线上）

```
① 确认范围      CHANGELOG「未发布」段已写齐，自评该升哪级（对照第 1 节）
② 改版本号      按第 3 节清单逐项修改
③ 本地验证      npm run build（含 tsc 类型检查）+ 冒烟测试 + 本次功能的实时验收
④ 提交          conventional commits，如 release: v1.1.0 M3 宠物系统
⑤ 推送          git push origin main（主分支直推，本项目为单人仓库）
⑥ 打标签        git tag -a vX.Y.Z -m "vX.Y.Z：一句话说明"
⑦ 推标签        git push origin vX.Y.Z
⑧ 建 Release    在 GitHub 创建 Release，notes 复制 CHANGELOG 对应段落
⑨ 确认线上      Cloudflare Pages 自动部署完成后，浏览器实测核心功能
⑩ 收尾         向用户汇报版本号、tag、Release 链接、线上地址
```

**不可跳过的步骤**：③ 验证、④ 提交信息、⑥ 标签。验证跳过 = 带病发布；标签跳过 = 版本号与代码快照脱钩，回滚和追查都失去锚点。

## 5. 标签与 Release 约定

- **Tag 命名**：`v` + 三段号，如 `v1.0.0`、`v1.1.0`、`v1.1.1`；使用 annotated tag（`git tag -a`，带说明信息）
- **Release 标题**：`vX.Y.Z · <阶段/主题>`，如 `v1.0.0 · M2 阅读核心`
- **Release 正文**：直接搬 CHANGELOG 对应段落（新增/变更/修复/技术内部），保持两处一致
- **回滚**：先修后发，不删已发布的 tag/Release；线上严重问题时发 `X.Y.Z+1` 热修复版，流程可压缩但不可跳过验证与 CHANGELOG

## 6. CHANGELOG 书写约定

- 位置：仓库根目录 `CHANGELOG.md`，遵循 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) 结构
- 分类（本项目惯用五项，按需增删）：**新增 / 变更 / 修复 / 移除 / 技术内部**
- 每条一行、说人话、写用户可感知的结果，不写实现细节流水账（实现细节放「技术内部」）
- 许可：CHANGELOG 随源代码采用 Apache-2.0（根目录文件默认跟随代码许可）

## 7. 提交信息规范（conventional commits）

| 前缀 | 用途 | 是否升版本 |
|---|---|---|
| `feat:` | 新功能 | 升次版本（或主版本，若涉架构） |
| `fix:` | Bug 修复 | 升修订号 |
| `refactor:` | 重构（无行为变化） | 视范围：架构级升主版本，否则修订号 |
| `docs:` | 文档变更 | 升修订号 |
| `chore:` | 构建/配置/杂务 | 升修订号 |
| `release:` | 发版提交（改版本号那一下） | 按本次定级 |
| `test:` | 测试相关 | 一般随所在变更合并，不单独发版 |

格式：`前缀: 一句话说明（中文，说清做了什么）`。

## 8. 预发布版本（预留）

当前为主站早期阶段（v1.0.0 已发布、主站已对外开放），暂不使用预发布号。将来如需公开测试：

- 版本号形如 `X.Y.Z-alpha.N` / `-beta.N` / `-rc.N`，tag 同名（如 `v1.1.0-beta.1`）
- 预发布版不计入正式版本线，转正时发正式的 `X.Y.Z`
- Release 标记为 Pre-release

## 9. 快速对照表

| 你这次做的事 | 升到 |
|---|---|
| 修了个 Bug、改了文案、同步了文档 | 1.1.**X** |
| 上线新模块/新页面/新功能 | 1.**X**.0 |
| 换框架、重构四层架构、不兼容数据迁移 | **X**.0.0 |
| 只是提交代码没发版 | 不动版本号 |
